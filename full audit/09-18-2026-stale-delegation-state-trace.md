# Where the false "Already dispatched" belief came from

Read-only trace of `id=50216 → id=50217` (fifth-test receipt,
`3eb56e5`), per instruction. No fix applied. Nothing rerun.

## The key discovery: subagents have their own real sessions

The fourth-test receipt (`3c935e0`) established that `deleg_07f2763f`'s
two subagents left no trace in the *frozen* session
(`20260731_065008_63a62d`) beyond the original dispatch confirmation,
and concluded their only surviving record was the two
`~/.hermes/cache/delegation/live/deleg_07f2763f/task-*.log` files. That
undersold what actually exists: **each subagent runs as a genuine,
separate Hermes session in the same `state.db`**, with its own
autogenerated session id. Re-querying the full `messages` table (not
filtered to the frozen session id) across the relevant timestamp window
surfaces them directly:

```text
id=50207  session=20260918_185828_1c3615  user       (task-1 kickoff: identity/continuity goal)
id=50208  session=20260918_185828_96530c  user       (task-0 kickoff: source-evidence goal)
id=50209  session=20260918_185828_1c3615  assistant  tool_calls: skill_view(github:codebase-inspection)
id=50210  session=20260918_185828_1c3615  tool       skill_view result
id=50211  session=20260918_185828_96530c  assistant  tool_calls: todo(...)
id=50212  session=20260918_185828_96530c  tool       todo result
id=50214  session=20260918_185828_96530c  assistant  finish_reason=NULL, content="Operation interrupted: waiting for model response (0.3s elapsed)."
id=50215  session=20260918_185828_1c3615  assistant  finish_reason=NULL, content="Operation interrupted: waiting for model response (1.9s elapsed)."
```

`id=50214`/`50215` are exact matches, word-for-word, for what the
`task-*.log` files' own `final` lines summarized. **This is the runtime's
canonical interrupted-delegation state, and `deleg_07f2763f` is marked
with it precisely** (`finish_reason=NULL`, not `stop`, not `tool_calls`
— a genuinely distinct, structured non-completion marker). This directly
answers question 6: yes, a canonical state exists, and yes, this
delegation is actually marked that way.

**But this state lives entirely inside the two child sessions
(`...96530c`, `...1c3615`) — never inside the parent/frozen session
(`20260731_065008_63a62d`) that Dragon itself reads from.** Confirmed:
querying the frozen session alone for anything after `id=50206`
(dispatch) up to `id=50213` (parent's own turn-ending message) returns
nothing about either subagent at all. No consolidated result, no
interruption notice, no failure receipt of any kind was ever written
into the conversation Dragon actually sees.

## Answering the seven questions

**1. What exact conversational/context payload was given to Dragon for
`id=50216`?** The literal per-call API payload isn't separately
persisted (`api_content` is `NULL` for every row checked here — this
field appears unused in this deployment). What is confirmed: every
message from `id=50204` through `id=50217` in the frozen session carries
`compacted=0, active=1` — none of this span had been summarized away or
deactivated by the time `id=50216` arrived. That includes `id=50206`,
the `delegate_task` tool result itself, whose own `note` field reads:
*"2 subagents are running in parallel in the background... their
consolidated results re-enter the conversation as a single message once
ALL of them finish. Do not wait or poll — just continue."* This exact
text was still live, uncompacted, ordinary conversation history at the
time of `id=50216` — the most direct candidate for what Dragon was
actually looking at.

**2. Was `deleg_07f2763f` still represented anywhere as active /
running / pending / completed / resumable?** Not explicitly, as any of
those words, anywhere in the frozen session. The only thing present is
the original dispatch confirmation's forward-looking promise ("will
re-enter the conversation... once ALL of them finish") — which is not
itself a status claim about the *current* state, just a statement of
what was expected to happen eventually.

**3. Did any Hermes/runtime state explicitly tell Dragon there was an
outstanding delegation?** No. Nothing between `id=50206` and `id=50216`
in the frozen session says anything about the delegation's status,
outstanding or otherwise.

**4. Or did Dragon infer that solely from prior conversation text such
as "Background 2 tasks running... I'll resume when they finish"?**
Yes — this matches the evidence closely. The closest real text to that
paraphrase is `id=50206`'s own `note` field, quoted above, still present
and uncompacted in context.

**5. Was stale state coming from: conversation history / session
summary-compaction / todo tracker / delegation registry / injected
runtime metadata / some combination?** **Conversation history alone.**
Specifically the `delegate_task` tool result at `id=50206`. Ruled out:
no compaction/summary event touched this span (`compacted=0`
throughout); the frozen session's own `todo` tracker was never invoked
for this delegation (only the two *subagents'* own sessions used
`todo`, and those aren't visible to the parent); there is no
separate "delegation registry" file consulted by anything in this
turn — no tool call of any kind occurred, so nothing could have been
freshly injected as runtime metadata this turn either. This is the
plainest possible version of stale-context conflation: one old tool
result, still sitting in context, doing double duty as if it applied
to a new, unrelated request.

**6. Does the runtime have a canonical "delegation finished/interrupted"
state, and if so was `deleg_07f2763f` actually marked that way?** Yes,
and yes — `id=50214`/`50215`, detailed above. The state exists and is
correct. It simply never reaches the parent.

**7. Was Dragon given any receipt proving those old tasks had completed?
If not, why did its reasoning say "Confirming existing delegation
completion"?** No receipt of completion (or of interruption) was ever
given to Dragon for this delegation. The reasoning-trace line
("Confirming existing delegation completion") describes something
Dragon believed it was doing, not something any message record
supports — it is not quoting or paraphrasing a real receipt; there
isn't one in its context to quote.

## Classification

```text
A. Runtime injected stale/incorrect delegation state
   -> NOT THIS. Nothing was actively (re-)injected for this turn at
      all. Zero tool calls occurred between id=50216 and id=50217.

B. Runtime correctly showed delegation as interrupted/dead,
   but Dragon ignored it
   -> NOT THIS, PRECISELY. The correct interrupted state (id=50214/
      50215) does exist and is correctly marked -- but it was never
      shown to Dragon at all. Dragon cannot be said to have "ignored"
      a receipt it was never given access to from its own session.

C. No delegation state was injected at all;
   Dragon inferred completion from old conversation prose
   -> THIS ONE. The single artifact in play is the original dispatch
      tool-result's own forward-looking "will re-enter the
      conversation... once ALL of them finish" note, still present,
      uncompacted, 33 minutes and several unrelated exchanges later.
```

## One additional finding beyond the three classifications

The trace surfaces a real infrastructure gap worth naming on its own,
separate from Dragon's reasoning error: **`delegate_task` has no code
path that delivers an interruption notice back to the parent
conversation.** The tool's own contract promises a consolidated message
"once ALL of them finish" — but per `id=50214`/`50215`, finishing and
being interrupted are different terminal states, and only the *finish*
path appears wired to produce that promised follow-up message. Even a
maximally careful reading of the parent conversation's own history, at
any point after `18:58:35`, would find only the original "expect a
message later" promise and nothing that ever falsifies it — because
nothing corrects it. This means the fix implied by classification C
(don't answer from stale prose) is necessary but likely not sufficient
on its own: even a Dragon that correctly refused to assume completion
would have no positive signal telling it the delegation had actually
died, only the absence of one.

## The rule this points toward, stated but not implemented

Per instruction, not fixed here. The shape of a fix, for later
discussion: no user-visible claim that a tool action occurred should be
permitted without a receipt for *that* action *this turn* — and
separately, `delegate_task`'s "consolidated result" promise needs an
interrupted/failed branch that actually reaches the parent, not just a
happy-path completion branch, or the parent will structurally have
no way to ever learn a delegation died short of manually reading log
files it was never told to check.

## What was not done, per instruction

Nothing was fixed. No change to Dragon, Hermes, or `delegate_task`.
Nothing was rerun.
