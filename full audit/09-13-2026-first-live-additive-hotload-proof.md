# First live end-to-end proof of additive runtime hot reload

## Claim this receipt closes

One real DIRECT_WRITE mutation was created by Dragon/Hermes, landed
exclusively in `scenes/WorldComposition.tscn`, and appeared in the
ALREADY-RUNNING composed game — same process, no restart — while
`scenes/Main.tscn` was never touched, the Editor→Dragon coordination
loop completed automatically, and the HUD/session transcript continued
uninterrupted.

This closes the additive-hotload milestone from
`09-13-2026-main-worldcomposition-ownership-split.md`. It does not, by
itself, establish anything about repeated turns, or about editing,
deleting, moving, or reconciling nodes that already exist — see Scope
below.

## Scope — what this does and does not prove

**Proven, now, with independent evidence:** one real DIRECT_WRITE
mutation hot-loaded into the already-running world through
`WorldComposition.tscn`, additively (a brand-new, self-contained scene
instanced once), with `Main.tscn` untouched, validation returned,
Dragon's automatic reaction, and the exact same runtime process alive
throughout.

**Not yet proven — explicitly out of scope for this receipt:**
- Repeated hotloads across many successive turns (stress/durability
  over time — this is n=1).
- Editing or replacing a node that already exists in
  `WorldComposition.tscn`.
- Deleting a node from `WorldComposition.tscn` and having the live
  tree reflect the removal (`RuntimeSceneSync3D` has no delete path at
  all — additive-only by design, see its own doc header).
- Moving/reparenting an existing node.
- Any reconciliation logic beyond "a name that wasn't known before is
  now present, and matches the one shape this loop understands."

None of the above were exercised by this probe and none should be
assumed to work from this receipt alone.
