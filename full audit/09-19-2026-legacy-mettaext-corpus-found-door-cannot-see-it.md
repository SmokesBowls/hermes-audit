# The historical Mettaext corpus exists — the door was never built to look at it

Read-only investigation, per instruction. Nothing ingested, rebuilt,
migrated, or modified. Confirms the user's hypothesis precisely: the
recent chapter-1 "controlled ingestion" proved the new continuation
loop works, but it did not prove the door is seeing Mettaext's real,
pre-existing output — because a substantial historical corpus exists,
and the door was never built to look where it lives.

## Why `engain_door.py` reports `002_molten_descent.md` as `not_ingested`

Read `engain_door.py`'s own `resolve_status()` (`:104-171`) in full. Its
entire ingestion check is:

```python
stem = source.stem  # e.g. "002_molten_descent"
passA_path = chapterroom_root(engain_root) / f"out_passA_{stem}.json"
if not passA_path.exists():
    return {"ingestion_status": "not_ingested", ...}
```

`chapterroom_root()` resolves to exactly one path:
`$ENGAIN_ROOT/tier3/mettaext/stageroom/output/chapterroom/`. This is
the **entire** ingestion check — one fixed directory, one fixed
filename pattern (`out_passA_<stem>.json`), one fixed JSON schema (it
goes on to read `chapter_id` and `source_file` keys from that file).
There is no fallback, no secondary location, no format-detection step.
If a file matching that exact path/name/schema doesn't exist, the
answer is `not_ingested` — regardless of what else exists anywhere
else on disk.

**Direct answer to the question asked: not "cannot see," not "doesn't
recognize the format" as a bug, not "absent" — it is structurally
never looking anywhere else.** The door was built to check one
location only; it was never given a second path to consult.

## Confirmed: this is a genuine schema/location mismatch, not a corrupted or unreadable format

Direct comparison, both read successfully as valid JSON:

```text
Legacy (legacy_pipeline_work/002_molten_descent.zonj.json):
  @id, @when, @where, @scope, @entities, =segments, =inferred, =metadata

Current (chapterroom/out_passA_001_the_ethereal_vigil.json, freshly
generated by this week's own controlled ingestion):
  contract, authority_state, chapter_id, source_file, title, book_hint,
  era_hint, line_count, word_count, raw_text
```

Completely different key sets, completely different top-level shape.
`resolve_status()` specifically reads `chapter_id` and `source_file`
from whatever file it finds at the expected path — neither key exists
in the legacy schema at all. Even if the door *did* somehow look inside
`legacy_pipeline_work/`, it could not parse this older format as a
valid Pass A artifact without translation.

## An uncomfortable but important corollary: chapter 1's own legacy output already existed too

```text
legacy_pipeline_work/001_the_ethereal_vigil.zonj.json   (exists, June 2026 dated)
legacy_pipeline_work/out_pass2_001_the_ethereal_vigil.metta
```

This means the "controlled ingestion" proved out in the ninth-live-test
receipt (`2872683`) — the one that generated 39 new evidence files and
finally let Dragon answer a real question about chapter 1 — **ran
against a chapter that Mettaext had already processed three months
earlier**, in a format the door simply never looked for. The new
pipeline run was not wrong, and nothing about the fixes already shipped
(`f1d873e`, `f11c900`, `bc995d1`, `cb8456c`) needs to be undone — but
it demonstrates the door working end to end, not the door correctly
recognizing pre-existing Mettaext evidence. Those are different
claims, and only the first one has actually been proven live so far.

## What this changes about the recovery question

Restating the user's own diagnosis, confirmed correct by this
investigation: **the right recovery operation, if any is wanted, is
connecting the door to the existing corpus (or migrating/converting
110 already-extracted chapters into the current schema once), not
running 139 more individual Dragon-triggered ingestions.** Each
individual ingestion this week (chapter 1's) is a real, correctly-
authorized, correctly-scoped write — but doing that ~135 more times to
reproduce work already sitting on disk in a different format would be
solving the wrong problem.

This investigation does not recommend which recovery path to take
(read the legacy schema directly, write a one-time offline migration,
extend `resolve_status()` to check a second location/format, or
something else) — that's a real design decision with its own tradeoffs,
not something to decide unilaterally here.
