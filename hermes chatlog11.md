    14. Trigger-policy feasibility
    
    Before every provider turn
    
    Possible now: yes.
    
    The worker sees every validated provider-bound turn in one place. It could call MettaText before prepare_image_dispatch().
    
    Implications:
    
    - strongest guarantee that all Dragon reasoning receives authored context;
    - one retrieval on every successful provider-bound submission;
    - increased latency and availability dependency;
    - requires a deterministic failure policy;
    - no current cacheable world/story identity exists, so this is the only immediately available policy that cannot silently miss a context transition.
    
    Only when Dragon explicitly requests authored context
    
    Possible now: not within the same reasoning turn.
    
    The Runtime Dragon provider:
    
    - has no tools;
    - receives one prompt;
    - returns one strict response;
    - cannot pause mid-turn and call MettaText.
    
    A genuinely Dragon-decided request would require a second-stage protocol, for example:
    
    text
    provider response:
        METTATEXT_REQUEST
    
    worker:
        validates request
        calls MettaText
        invokes provider again with result
    
    
    That does not exist.
    
    A player-text keyword router would be possible, but that would be the caller heuristically deciding—not Dragon explicitly requesting context after reasoning.
    
    When world/perception identifiers indicate context is needed
    
    Mechanically possible, semantically weak today.
    
    Available identifiers:
    
    text
    project_id
    scene_path
    client_request_id
    capture_id
    current_location
    player_position
    
    
    But:
    
    - project_id is constant;
    - scene_path is constant;
    - client_request_id is new every submission;
    - capture_id is new every submission;
    - current_location is hardcoded;
    - player_position is not a story/world identity.
    
    Using unique capture IDs would reduce this policy to “every turn.” Using the constant project/scene would reduce it to “once forever.” Neither detects actual story relevance.
    
    This policy needs a stable authoritative semantic world reference first, such as:
    
    text
    world_id
    occurrence_id
    scene_instance_id
    location_id
    story_scope_id
    world_revision
    
    
    Those identifiers do not exist in the current Dragon perception contract.
    
    Combination policy
    
    Architecturally possible, but it requires both missing capabilities:
    
    text
    stable world/story identifiers
    + a second-stage Dragon-requested retrieval protocol
    
    
    A future combination could be:
    
    text
    first encounter or changed semantic world revision
        → automatic context retrieval
    
    same stable world context
        → reuse bounded cached artifact by hash
    
    Dragon detects an unresolved authored question
        → explicit second-stage MettaText request
    
    unrelated conversational turn
        → no new retrieval
    
    
    The current architecture does not provide enough evidence to choose that as an implemented production policy.
    
    Bounded conclusion:
    
    - “Before every provider turn” is the only policy directly supportable by the present single-pass caller without new routing state.
    - “Dragon explicitly requests it” requires a second provider round.
    - “World IDs trigger it” requires better authoritative identifiers.
    - The audit does not justify silently choosing the final production policy.

    17. Redundant or unavailable fields from the previous proposal
    
    Changed after inspecting Dragon:
    
    call_id
    
    Redundant. The current Dragon requires call_id == request_id.
    
    new semantic request ID
    
    Redundant for the first one-retrieval-per-Dragon-request proof. Reuse request_id. Add a child-attempt ID only if retries or multiple semantic calls per turn are later introduced.
    
    shared_session_id
    
    Not generally available in the canonical path. It may be optional metadata under continuity mode, but must not be required.
    
    turn_id
    
    Unavailable before the provider call in the real caller. It cannot correlate the initial MettaText request.
    
    question/problem plus player_input
    
    Redundant. A single query_text, populated from validated player_input, is enough initially.
    
    entity/location/topic hints
    
    Not necessary for the first proof. Requiring Dragon-side extraction would move semantic intake back into Dragon. MettaText should derive candidates from query_text and bounded
    structured context. Explicit hints may remain optional.
    
    requested semantic domains
    
    Not necessary initially. MettaText is supposed to classify and route the material. Making Dragon enumerate domains would partially recreate the fan-out architecture being removed.
    
    source scope
    
    A raw storage scope is forbidden. A logical authored scope could be added later, but the first caller has no reliable story-scope identifier.
    
    retrieval limits
    
    These can initially be MettaText service policy rather than caller-controlled fields. The caller needs a bounded response but does not necessarily need to select the limits.

    Too vague. The actual caller provides a concrete observation_ref composed from existing validated fields.
